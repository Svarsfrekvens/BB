# Flora: local duty-domain experiment, 2026-10-21

This branch adds an opt-in **experimental** `EXPLICIT_NO_BREAK_SCENARIO` mode to the Flora method. The existing solver-placed-break mode remains the default and its saved results are untouched. The experiment models active-only candidate duties from 4 through 13 hours, including 6, 7, and 8 hours. A combined work/on-call/work duty is a separate whole duty: its overall span is not cut to the active-only 13-hour limit.

In the new mode, source breaks must be absent, the solver generates no breaks, ordinary targets must be supplied in the same no-break minute accounting, and any new active-only candidate longer than 13 hours is rejected. The independent validator rejects inserted breaks and active-only duties above 13 hours. The run is identified as `joint-shifts-no-break-experiment/v0`; no-break applicability is reported as unknown for contractual/legal review, not silently approved.

Local synthetic tests cover 4, 6, 7, 8, and 13-hour active-only duties without breaks; 3 and 14 hours are rejected. A fixed 24-hour work/on-call/work duty remains intact and without a generated break. This branch also adds an **optional**, exactly timed 24-hour `Ar–Jo–Ar` candidate as one indivisible solver decision. Its active parts count toward customer capacity and ordinary/temporary active minutes; the `Jo` part counts separately toward on-call time and its rolling cap. All three parts share one generated pass identity and are checked together by the independent validator. The candidate requires a sleep-on-call-qualified person and at least five hours of contiguous night on-call. Historical approved pass identities are source evidence only, and sick-time rows never become work or on-call.

The importer accepts such candidates only from an explicit, sourced `LOCAL_MODEL_EXPERIMENT` profile entry. It never generates them automatically from the approved historical source or the browser workspace. To keep aggregate capacity accounting exact, this first experiment rejects possible active-work windows that overlap for the same employee; broader competing candidate domains require a separate encoding. No future Flora duty dates or employee availability have been inferred from the historic roster.

The independent review also found that a hypothetical whole-duty candidate could overlap the same person's locked source work. This is now rejected before building the optimizer model, as is an overlapping active-only candidate in the no-break experiment. Candidate IDs may not collide with original source row IDs. Malformed whole-duty profile entries receive an import review error instead of an internal exception. Focused regression tests cover each case.

Two local probes used the same saved Flora request and the reviewed historical-pass profile, copied into memory. Both removed the profile's mathematical reference breaks and recomputed ordinary targets from source `Ar` gross minutes; neither changed the installed profile or sent a job to the remote engine. The first kept the existing 55 candidate windows; the second widened 54 windows from a 10.5-hour maximum to 13 hours within their existing clock windows. The one more restricted window was retained.

|---|---:|---:|---:|---:|---|
| No-break; original candidate windows | 1,451 / 1,451 | 30,930 | 8,275 | 0 | PASS |

Both searches returned `FEASIBLE` within a 12-second budget per objective stage, **not** an optimum for temporary time. The temporary-minute totals must not be interpreted as a proven benefit or loss from widening windows. They are also not directly comparable with the old break-deducting result. Those probes did not include new optional whole-duty candidates; they test the active-only duration and no-break accounting. Whole-duty selection has passed synthetic tests, but a real Flora comparison needs a separate explicit future candidate domain and availability source.

## Historical Flora replay

`motor/experiments/replay_flora_approved_duties.py` performs a local holdout replay using paths to the saved request, reviewed profile and clean historical-example catalog. It does not submit an engine job or modify any input file. The script removes 15 clean P2 duties from the fixed source schedule and offers the **same person and exact source times** back as optional candidates: eleven 24-hour `Ar–Jo–Ar` whole duties and four 11-hour active-only duties. G24 starts in P1 and remains fixed history. The eight sick-affected source groups are not converted to candidates.

The independent result check passed: 13 of 15 held-out duties were selected, all 1,451 source needs were mathematically covered, ordinary active time was 30,930 minutes, temporary active time 6,765 minutes, on-call time 11,070 minutes, and generated break time was zero. G02 and G13 were not selected in this feasible result. Coverage stages were optimal, but the temporary-time stage was only `FEASIBLE` within a 20-second search budget, so the selected set is not an optimality claim. The seven remaining unknown checks include no-break applicability, full daily-rest boundary evidence, and contract accounting. The replay shows the candidate encoding can use real Flora source rows; it does not determine a future roster or prove that omitting breaks is contractually allowed.

Verification: all 517 motor tests passed for the reviewed branch (6 skipped), including focused checks for complete selection, pass identity, break-free accounting, night on-call eligibility, rolling on-call cap, sick-time rejection, malformed or overlapping candidate rejection, and rejection of a tampered partial result. The historical replay was rerun after the review and again selected 13/15 clean duties with 1,451/1,451 needs covered and independent PASS. No live profile, saved motor result, business workspace, or published app was modified.

## Readiness for future dates

The reviewed Flora profile currently has 55 candidate windows, all dated 11 May–5 June 2026. Fifty-four have a 630-minute maximum and one a 420-minute maximum. It has no future-dated window and no whole-duty candidate entry. The profile's latest applicable period ends 7 June 2026. Thus the source supports the historical holdout replay above, but **no future Flora availability or 13-hour/24-hour candidate domain is evidenced by this profile**. A rolling-four-week copy can be used as an explicitly hypothetical calendar test, but it would not establish actual availability or replace a new planning period's needs and staffing decisions.

## Explicit rolling-four-week hypothesis

`motor/experiments/roll_flora_four_week_hypothesis.py` repeats the relative historical source rows, needs, candidate windows, and clean held-out duties on a future Monday that is an exact multiple of four weeks later. It labels the copied rows as assumptions, replaces the historical input digest with a distinct scenario fingerprint, and writes only an aggregate local summary. It never submits a job or writes a business workspace. The 54 generally available candidate maxima are expanded from 10.5 to 13 hours inside their existing 15-hour clock windows for this test; the one seven-hour restriction and four held-out 11-hour examples stay as they were. Candidate *availability* is therefore still an assumption.

For 23 November–20 December 2026 (seven four-week cycles after Flora P2), the solver returned `FEASIBLE`, with 1,451/1,451 **repeated** needs covered, 11 optional whole work/on-call/work duties selected, 30,930 ordinary active minutes, 6,795 temporary active minutes, 11,070 on-call minutes, and zero generated breaks. The independent checker returned PASS with no violations; seven checks remain unknown. Selected active-only candidate lengths included four and six hours, while the synthetic unit tests separately prove that seven, eight, and 13 hours are allowed. The final objective stage was only `FEASIBLE`, not proven optimal. This is a technical model/calendar exercise with copied historical fixed rows and needs, **not** evidence of real November staffing, verified availability, an approved roster, or an economic saving.

## Longer search for the actual Flora P2 test period

With the reviewed P2 source and 54 candidate maxima expanded to 13 hours inside their existing clock windows, a 300-second final-stage search covered all 1,451 source needs with independent PASS. Ordinary active time was 30,930 minutes before and after. Temporary active time was 17,790 minutes in the no-break source reference and 6,660 minutes (111 h) in the candidate; on-call was 10,190 then 11,070 minutes. Generated breaks were zero. The first two objectives were OPTIMAL; temporary time remained FEASIBLE with a 6,310-minute lower bound, so 111 h is a found solution, not a proven minimum. None of these minute changes is a verified cost saving or a business approval.

Fourteen P2 rows for explicit planned work/on-call replacement of source `St` now inherit the **exact reviewed source row's** whole-duty ID when present. Their output basis is marked `PLANNED_REPLACEMENT_OF_REVIEWED_DUTY`; source sickness rows stay separate and unchanged. No ID is inferred from a row prefix or adjacent times. The reviewed P2 solution has pass IDs for every in-period work/on-call row. Twelve in-period absence rows correctly remain without pass IDs, as do 126 historical rows outside P2. The original all-row `pass_ids_complete` flag therefore remains false. A separate scoped `period_duty_pass_ids_complete` flag reports true for P2 duties, without claiming the full proposal is transferable or approved. The BB recipient still needs a complete, tested schedule-and-placement transfer model; the existing proposal-copy path only handles placements.
